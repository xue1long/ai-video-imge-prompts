## 0. 摘要

本方案规定 Midjourney Explore 镜像的**数据采集与累积策略**，核心约束一条：

> **榜单每天换血，本地数据只增不替——每天把新采集结果落到新批次目录，历史批次原样保留。**

经审计整改后，方案收敛为三件事 + 一条明文取舍：

1. **批次化存储**：`data/daily/<YYYY-MM-DD>/`，永不覆写已有批次。
2. **原图走直链**：`full` 档不落本地，站点与检索端**端到端**引用 CDN 直链；`thumb`/`mid` 本地化。
3. **浏览与累积解耦**：站点退化为**单分片 + 批次筛选**（近期预览），规模浏览交给 WebUI；不再按批次切分片。
4. **明文取舍**：本地化承诺以 `thumb`/`mid` 为准；`full` 为 CDN 引用，**长期耐久性不保证**（见 §1.2）。

审计删除了三处过度工程（详见 §8）：构建回写配置、全局突变计数、`full` 的本地路径+回落二元组。

### 1.2 目标达成度与根本取舍（审计新增）

严格对照原始目标 G1「下载新数据到本地，不替换」：

| 目标 | 达成 | 判语 |
|---|---|---|
| G1 不替换 | ✅ 结构性达成 | `daily/` 分区 + 抽取守卫，可靠 |
| G2 救 11-01 | ✅ 已落地 | — |
| G1 字面「数据到本地」 | ⚠️ **半达成** | 仅 `thumb`/`mid` 本地；`full` 为 CDN 引用（方案 A 的代价） |

**明文结论**：本方案真正**永久持有**的是 `thumb`/`mid` 与全部元数据；`full` 是「尽力引用」而非「本地归档」。若需永久留存原图，必须另行决策（本地化 `full` 的磁盘代价 ≈ 2.3 GB/天 vs CDN 失效风险），**不能默认本方案已满足**。

## 2. 术语

| 词 | 含义 |
|---|---|
| 批次（batch） | 一次采集结果，以采集日 `YYYY-MM-DD` 标识；一批 = 200 作业 = 800 图 |
| 作业（job） | 一次生成请求，4 格（`index` 0–3），共用一段 prompt |
| 档位（tier） | `thumb` / `mid` / `full`，策略各异 |
| 直链（online） | 直接引用上游 CDN URL，本地不存文件 |
| 分片（shard） | 站点为控体积切分的 `.js` 数据文件；**整改后站点单一分片** |
| 派生（derived） | 由源数据再生成的结构（manifest / gallery 分片 / catalog DB），可重建 |

## 3. 数据架构

### 3.1 目录模型

```
sites/midjourney-explore/
├── data/
│   ├── daily/                      # 批次根（核心：只增不替；源数据）
│   │   ├── 2026-11-01/             # 一批 = jobs.json(200) + meta.json
│   │   └── 2026-11-02/
│   ├── manifest.json               # 累积索引（daily 展平，1600 行；派生可重建）
│   ├── manifest.csv                # 表格视图（派生）
│   ├── gallery.js                  # 站点数据单一分片（jobs + items；派生）
│   └── landing.json                # 落地页数据（派生）
├── thumbs/  mid/                   # 本地化档位（耐久资产）
└── index.html                      # 站点入口
```

**不覆盖保证**：
- `scripts/extract.py` 每日新建 `daily/<今日>/`，**目录已存在则中止**，绝不覆写。
- `scripts/manifest.py:load_batches()` 只读 `daily/*/jobs.json`，不写回 daily。
- 源数据 = `daily/`；其余（manifest / gallery / landing / catalog）均为**可重建派生**，不得反向作为源。

**清理项（已完成，W6）**：`data/jobs.json`（旧单快照）、`data/meta.json` 已删除 —— 二者被 `daily/2026-11-02/` 完整取代（id 集合逐一比对一致）。

### 3.2 manifest 字段契约

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | `<jobId>_<index>` 唯一键 |
| `jobId` | str | 作业 UUID（4 格共用） |
| `index` | int | 0–3 |
| `batch` | str | 采集日 `YYYY-MM-DD`（筛选键） |
| `prompt` | str | 原文提示词（不改写） |
| `title`/`aspect`/`version` | str | 标题 / 宽高比 / 模型版本 |
| `username`/`displayName` | str | 作者 |
| `width`/`height` | int | 原图尺寸 |
| `sref` | str | 风格参考码（如有） |
| `sourceUrl` | str | 上游作业页 |
| `thumb_url`/`thumb_path` | str | 缩略图：上游 URL / 本地相对路径 |
| `mid_url`/`mid_path` | str | 中图：上游 URL / 本地相对路径 |
| `full_url` | str | 原图 CDN 直链（方案 A：**只此一列**，不设本地 `full_path` 语义） |
| `_ck_url` | str | 上游校验/备用地址 |

> **W6 已落地**：`full_path` 字段已从 manifest 里删除（不是留着指向已删文件的空壳）。
> 理由：留一个指向不存在文件的路径字段，等于给下游埋必然 404 的死值 ——
> 站点数据里的 `gPath`、索引里的 `sites/<集合>/img/…` 都是它的产物。
> 回归：`MjFullOnline.test_manifest_has_no_full_path` / `test_gallery_has_no_full_path_field`。

### 3.3 取图策略（imagePolicy，整改后）

```json
"tiers": ["thumb", "mid"],
"imagePolicy": { "thumb": "local-only", "mid": "local-only", "full": "online" }
```

| 档位 | 策略 | 本地 | 上游 | 入库地址 |
|---|---|---|---|---|
| `thumb` | local-only | ✓ | url 备用 | 本地相对路径 |
| `mid` | local-only | ✓ | url 备用 | 本地相对路径 |
| `full` | **online** | ✗ | ✓ 直链 | **CDN URL（直接入库）** |

**统一约定（关键接口）**：档位地址为 `http(s)://` 开头时，`sync` **不得**拼接 `sites/<集合>/` 前缀，直接以外链入库。`full` 端到端 online，不保留「本地路径 + 302 回落」二元组（审计删除项，见 §8）。

## 4. 采集与构建流水线

每日顺序：

```
extract.py  →  写 data/daily/<今日>/{jobs.json, meta.json}      （新增批次，不覆写）
manifest.py →  合并 daily → manifest.json + manifest.csv        （累积）
fetch.py    →  仅下 tiers=[thumb,mid]（full 跳过）                （省 ~2.3 GB/天）
build.py    →  hub + 站点（单分片、批次筛选、统计从 manifest 现算）
sync.py     →  重建检索索引（批次分面 + full 外链入库）
```

| 环节 | 关键文件 | 备注 |
|---|---|---|
| 抽取 | `scripts/extract.py` | 已存在目录则中止；**失败需非零退出** |
| 累积 | `scripts/manifest.py:load_batches()` | 只读 daily，展平合并 |
| 下载 | `tools/fetch.py` | `tiers` 取自 `sites.json`；`Referer` 取 `source` |
| 构建 | `scripts/build_gallery.py` | 单分片；统计**从 manifest 现算**（不再回写 `sites.json`、不再做占位符回填） |
| 入库 | `index/sync.py` | `full` 存 `full_url`；`thumb`/`mid` 存本地路径 + url 回落 |

### 4.1 失败监控（审计新增，系统级缺口）

每日采集是静默累积，失败即静默丢数据。最低要求：

- 构建/采集结束时断言：`manifest` 行数较上次**有增长**（或本批 `jobId` 去重后 > 0）；
- 断言失败 → 非零退出并打印明确原因（哪个环节、缺哪批）；
- 不引入独立监控系统，仅用退出码 + 日志满足「不静默丢失」。

## 5. 站点架构（整改后：单分片 + 批次筛选）

> **审计整改**：取消「按批次切多个分片 + 默认全部分片 + 双层分面状态机」。依据：当前全量仅 ~860 KB，属过早优化；且 §9 承认 30 天规模即失效，非终局可存续。

| 项 | 整改后 |
|---|---|
| 数据文件 | `gallery.js` **单一分片**（全量或「近期 N 批」，N 由构建参数定） |
| 批次维度 | `#batchChips` 作为**普通筛选项**（前端过滤），不再决定加载哪个分片 |
| 宽高比维度 | `#aspChips`，计数按当前筛选结果实时算 |
| 首屏预算 | 单分片体积可控（近期 N 批）；历史规模交给 WebUI |
| 灯箱 | 缩略 `it.t`、中图 `it.m` 本地；原图 `it.g` = `full_url` 直链 |

理由（终局思维）：29 万图无法在静态页客户端过滤，静态站终局角色 = **近期预览**；按日规模浏览由 WebUI（服务端分页）承担，故站点不再投入批分片复杂度。

## 6. 检索端架构（WebUI）

### 6.1 批次分面

- `index/catalog.py` 本站分面：`{"版本":"version","批次":"batch"}`，外加派生分面
  `derived_facets = {"类别": [("sref", "有 sref 码")]}`——manifest 里没有「类别」字段，
  sref 非空即打这条标签，左栏点它只看得到带 sref 码的作业。
- 「宽高比」与「风格参考」两维已撤（2026-11-03）：宽高比 29 种、长尾每个只有 4 张；
  风格参考一码一条，是标识而不是分类。两维做左栏分面噪声都大于信息。宽高比字段仍在
  manifest 里（站点页面的徽标要用），由 `ignored: ["aspect"]` 声明「索引不用」，
  不报未映射字段。
- 成本低、支撑「按日累积」心智模型，**保留**。

### 6.2 档位寻址（整改后：单一口径）

- `catalog.file_addr(sid, kind, rec, key)` 统一走 `shared/image_policy.tier_addr` —— 站点构建与索引导出**同一套判断**，不各写一份。
- `full`：`tier_addr` 返回 `online` → 地址 = `full_url` → `sync` 以外链入库（不加前缀）。
- `thumb`/`mid`：地址 = 本地相对路径，`url` 作加载失败回落。
- **删除**：`file_specs` 对 `full` 返回「本地路径 + 上游 URL」二元组的过渡写法（img/ 清空后本地路径成死值）。

### 6.3 三选项

- `styles / images / videos` 已在 WebUI 落地（commit `ec510f5`）：图像 / 风格 / 视频 0。
- 站点侧三选项：按用户决议暂缓（R8）。

### 9.1 风险

- **CDN 耐久性（首要）**：`full` 依赖上游直链，长期可能失效；本方案不承诺原图永久留存（§1.2）。若业务要求归档原图，须重新决策。
- **派生漂移**：manifest / gallery / catalog 三份派生各自可失败；任一未重建即与源不一致。构建流水线须保证「改了上游就全链重建」。
- ~~**R4 未实测**~~：已消除。实测还额外暴露了灯箱横向溢出（stage 2658px > 视口 900px）——**布局类改动不实测就会漏到线上**。
- **服务进程跑旧代码**：实测时曾出现「代码已修但 serve 进程未重启」，接口吐出 `/media/https://…` 这种必然 404 的地址。**实测前先确认进程已加载当前代码**。

### 9.2 实测环境备注（2026-11-02）

`cdn.midjourney.com` 从本机访问返回 **403**，已核实为 **Cloudflare 人机校验**（响应头 `Cf-Mitigated: challenge` + `CF-RAY: …-HKG` + 挑战页 body），非链接失效；同刻 `raw.githubusercontent.com` 正常 200。真实浏览器带正常指纹不受影响。
因此 `full` 档的验收口径是「**地址是纯 CDN URL + 媒体路由 302 直通**」，可达性由上游负责。

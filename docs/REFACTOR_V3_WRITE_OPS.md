# 重构方案 v3：素材的四类写操作

> 本文是 [`REFACTOR_V2.md`](REFACTOR_V2.md) 的续篇。v2 解决「数据怎么存、怎么查」，本文解决「数据怎么改」。
> **定稿见 [`REFACTOR_V4_CREATION_FLOW.md`](REFACTOR_V4_CREATION_FLOW.md)** —— 按「创作取素材」重心重排了优先级（出口层提前、管理功能后置），本文的库边界与删除三档设计被原样继承。
> v2 的架构**假设这个世界是只读的**（图片原位索引、DB 只存路径）。一旦支持导入与删除，这个前提失效，必须先重新划定库的边界。
> 状态：**待确认**，未改动任何代码。日期：2026-10-31

## 一、第一性原理：写操作只有三类原子动作

界面上的按钮可能有二十个，但落到系统里只有三类动作：

| 原子动作 | 例子 | 可逆性 | 成本 | 风险 |
| --- | --- | --- | --- | --- |
| **元数据变化** | 改标题、打标签、改 prompt、收藏 | 完全可逆 | 几十字节 | 极低 |
| **关系变化** | 加入集合、关联派生图、合并重复 | 可逆 | 几行 | 低 |
| **文件系统变化** | 导入、删除、移动、导出文件 | **部分不可逆** | GB 级、慢 | **高** |

**风险差三个数量级。** 所以第一个硬结论：

> **元数据写与文件写必须在代码层彻底分离。** 不能出现「一个函数既改 DB 又删文件」。

v2 的方案里只有 `item.deleted_at`（软删），没有文件操作层——这是缺口。补它的时候，第一个问题不是「怎么写」，而是「写在哪」。

### 1.1 「修改」其实是三件不同的事

「素材修改」这个词有歧义，拆开看是三条完全不同的路：

| 用户想干什么 | 正确做法 | 为什么 |
| --- | --- | --- |
| 改标题 / 标签 / prompt | `UPDATE item`（元数据） | 可逆、零成本 |
| 改图本身（裁剪、转换格式、压缩） | **生成派生**（新文件，原图不动） | 改了原图就无法追溯，也没法回滚 |
| 换成更好的版本 | **新 asset，旧的标 superseded** | 版本链，不覆盖 |

所以：**素材管理器不该内置图像编辑器。** 要裁剪要调色，去 PS / ComfyUI 做完再导入回来。库里只提供「替换图」这一条窄路。

### 1.2 「导入」是两件不同的事

v2 的 Step 1 做的是**元数据导入**（图已在盘上，只对齐 DB）。你说的「导入」大概率是**素材文件导入**（新图进来）。两者成本差两个数量级：

| 类型 | 输入 | 是否需要读图 | 耗时 |
| --- | --- | --- | --- |
| 元数据导入 | `manifest.json` / CSV | 否 | 秒级 |
| 素材文件导入 | 一堆 jpg/png | 是（尺寸 + 缩略图） | 每张 50–200ms |

**必须分开实现**，否则「导入」这个按钮永远说不清自己干了什么。

### 1.3 「删除」是三个层次

几乎所有素材管理器把三个层次混成一个「删除」，于是用户不敢点。正确做法是分离：

| 档 | 语义 | 文件 | DB | 恢复方式 |
| --- | --- | --- | --- | --- |
| ① 隐藏 | 从视图移除 | 保留 | `deleted_at` 置位 | 回收站一键恢复 |
| ② 移出库 | 不再被管理 | 保留（变孤儿） | 删除记录 | 只能重新导入 |
| ③ 物理删除 | 释放磁盘 | **删除** | 删除记录 | **不可恢复** |

### 1.4 「导出」是四种

| 类型 | 用途 | 体积 | 现状 |
| --- | --- | --- | --- |
| ① 元数据 CSV/JSON | Excel、备份、给别的程序 | KB | 无（v2 提了 `export.csv`） |
| ② 文件导出到目录 | 喂给 ComfyUI、设计软件 | GB | 无 |
| ③ 可迁移包 | 换机器 | GB | 无 |
| ④ 静态站 | 发布 | GB | **已有** `tools/release.py` |

## 二、批判性思维：v2 有四个判断是错的

| # | v2 的说法 | 错在哪 | 修正 |
| --- | --- | --- | --- |
| 1 | 「图片不搬，DB 只存路径」 | 只在只读世界成立。支持导入后，新图必须有落点 | 划分只读区 / 可写区 |
| 2 | 「导入低频，砍掉/推后」 | **频率低是设计造成的，不是需求本身**。如果导入要关服务、跑脚本，那用户永远不导入——一个不能加素材的库是死的 | 导入必须做到「拖一下就行」，并进核心 |
| 3 | 「零依赖，三档图已在盘上」 | 导入新图必须生成缩略图，Pillow 变成必需 | 接受 1 个依赖，且只在导入路径 |
| 4 | 「删除用 `deleted_at` 软删」 | 软删不释放磁盘。portrait 的 4.66 GB 原图 PNG 删不掉就白占 | 三档分离，物理删除受 §3 约束 |

第 2 条是这次最该被批判的。**二八法则只看频率会骗人**：导入的频率确实低，但它决定库是活的还是死的。频率低是因为成本高；成本降下来，频率自然上去。

第 1 条更关键——它不是我写错了，是**只读视角下看不见的问题**。这正是「写操作」这个需求带来的架构分叉。

## 三、库的边界（本方案的核心决策）

写操作一进来，第一个要回答的问题是：**库的边界在哪？**

| 方案 | 内容 | 评价 |
| --- | --- | --- |
| A | 库 = `sites/`，导入就往现有目录写 | 破坏 v2 的零拷贝前提；新旧素材混在一起分不清；`release.py` 的语义被污染 |
| B | `sites/` 只读 + 新增 `library/` 可写 | **采用** |
| C | 任意多个已注册的卷 | 终局方向，但现在过度设计 |

**裁决 B**，并配一条硬约束：

```
sites/        只读区    11.63 GB 采集素材    永不物理删除
library/      可写区    你自己导入的素材     允许物理删除
  └── 2026/10/...                              按年月分目录
gallery.db    唯一真相
backups/      DB 快照（批量操作前自动打）
```

> **硬约束：物理删除只作用于 `library/`。**

这一条的价值远超技术层面：

1. **误操作的代价被结构性限制住**——你不可能删掉那 11.63 GB 需要重新下载几个小时的采集素材
2. **旧链路永远能跑**——`tools/release.py` 发布前会校验图片，`sites/` 完整则永不中止
3. **权限按来源分配，而不是按用户意愿**——不需要「确认三次」的弹窗恐吓，结构上就删不掉

想在库里「去掉」一张采集来的图？用软删（视图消失，文件保留）。这就是为什么第①档删除存在。

## 四、四类操作的详细设计

### 4.1 修改（元数据）

三个层次，风险递增：

| 层 | 操作 | 接口 | 保护 |
| --- | --- | --- | --- |
| 单字段 | 标题 / prompt / 作者 / 来源 | `PATCH /api/items/{id}` | 记旧值到响应的 `undo` 字段 |
| 标签 | 增删 tag（区分 builtin / manual） | `POST/DELETE /api/items/{id}/tags` | 内置标签只读，手动可删 |
| 批量 | 对**当前筛选结果**批量打标 / 改字段 | `POST /api/bulk` | 批量前自动快照 + 影响行数预览 |

**批量操作的关键设计**：条件来自筛选，而不是前端传 5000 个 id。

```
POST /api/bulk
{ "filter": {"collection":"pose","facets":{"视角":"正面"},"q":"坐姿"},
  "action": {"type":"add_tag","ns":"用途","name":"参考"} }
→ { "affected": 1204, "snapshot": "backups/2026-10-31T18-22-01.db" }
```

先返回影响行数（前端弹「将影响 1,204 条，确认？」），确认后才执行。这样「筛选 → 全选 → 操作」是一条链，也是唯一能优雅处理「2 万条里改 5 千条」的方式。

**图像「修改」的窄路**：`POST /api/items/{id}/replace`（上传新图 → 新 asset，旧 asset 标 `superseded`，永不覆盖）。

### 4.2 导入

两种，分开做。

**A. 元数据导入**（v2 的 `sync.py`）：6 份 manifest → DB，秒级，幂等。

**B. 素材文件导入**（本次新增）：

```
输入：拖拽文件/文件夹 → POST /api/import {"paths":[...]} 或 multipart 上传
流程：
  1. 读尺寸（Pillow，或沿用项目已有的 PNG/JPEG 头解析）
  2. 生成缩略图（最长边 400px，webp 质量 82，与现有 thumbs 规范一致）
  3. 移入 library/YYYY/MM/
  4. 写 asset + 建 item（title 默认文件名去扩展名）
  5. asset.source_kind = 'own'
进度：后台线程 + GET /api/jobs/{id} 轮询（不引入 SSE/WebSocket）
```

关键性质：

| 性质 | 做法 | 为什么重要 |
| --- | --- | --- |
| 幂等 | 按「文件名 + 字节数 + 尺寸」判重（不算 sha256） | 同一个文件夹导两次不产生重复 |
| 可中断 | 每张图一个独立事务 | 导到一半取消，已导入的有效 |
| 不阻塞 | 后台 job + 轮询 | 导入 5000 张时 UI 不能卡死 |
| 可追溯 | `item.meta.source_path` 记来源目录 | 以后做「监视目录自动同步」的基础 |

> 要不要建 `source` 表（一个源 = 一个目录，可重复同步）？**现在不建**（奥卡姆）。用 `meta.source_path` 一个字段，等真需要「监视目录」时再提升为表。

### 4.3 删除

三档分离，UI 上必须是三个不同的按钮，不是一个「删除 + 回收站」。

| 档 | 接口 | 文件操作 | 提示文案要点 |
| --- | --- | --- | --- |
| ① 隐藏 | `POST /api/items/{id}/hide` | 无 | 「已移入回收站，可随时恢复」 |
| ② 移出库 | `DELETE /api/items/{id}` | 无（提示文件留在盘上） | 「记录已移除，图片文件仍在 `sites/` 下」 |
| ③ 物理删除 | `DELETE /api/items/{id}?purge=1` | 删文件 | 「将释放 2.3 MB，**不可恢复**」+ 二次确认 |

约束：

- 档③ 只允许 `source_kind = 'own'`（即 `library/` 里的）。`sites/` 的素材只能走档①②
- 档③ 必须显示将释放的体积，让「删」这个动作有可感知的收益
- 回收站自动清理：档① 超过 30 天的记录，提示「转为移出库 / 物理删除 / 继续保留」

**孤儿扫描（必须做，成本极低，一个功能顶三个）**：

| 检查 | 含义 | 处理 |
| --- | --- | --- |
| DB 有记录，文件不存在 | 被外部删了 / 盘没挂 | 标 `asset.status='missing'`，UI 显示占位 |
| 文件存在（仅 `library/`），DB 无记录 | 导入中断 / 手动拷进来 | 列出，可「导入」或「删除」 |

实现只要一个 SQL + 一次 `os.walk('library')`。它同时是导入的卫生检查和删除的安全网。

### 4.4 导出

| 类型 | 接口 | 用途 | 优先级 |
| --- | --- | --- | --- |
| ① 元数据 CSV/JSON | `GET /api/export?format=csv&filter=...` | 备份、Excel、给别的程序 | **最高** |
| ② 文件到目录 | `POST /api/export/files {target, filter}` | 喂 ComfyUI、设计软件 | 高（若重心是创作） |
| ③ 可迁移包 | — | 换机器 | **砍**（有①+文件复制就够） |
| ④ 静态站 | 从 DB 生成 manifest → 喂 `release.py` | 发布 | 按需 |

两条设计原则：

1. **导出范围 = 当前筛选**，不是全库。「筛出 200 张坐姿 → 导出到 ComfyUI 输入目录」是一条链。
2. **导出是只读操作**，永远不修改库。所以它最安全，也最该先做。

## 五、奥卡姆剃刀：写操作里能砍什么

| 候选 | 裁决 | 理由 |
| --- | --- | --- |
| 内置图像编辑器（裁剪/旋转/调色） | **砍** | 外面有 PS 和 ComfyUI，库不该是编辑器 |
| 版本链 UI（v1/v2/v3 对比） | **砍** | 保留 `superseded` 字段即可，不需要界面 |
| 操作日志表 + 撤销栈 | **砍**，换成 DB 快照 | `cp gallery.db backups/xxx.db`，几 MB，零代码，比任何撤销机制都可靠 |
| `source` 表 | **砍** | 一个 `meta.source_path` 字段够用 |
| 可迁移包格式 | **砍** | CSV + 文件复制 |
| 实时文件监视（watchdog） | **砍** | 手动触发一次扫描，秒级完成 |
| 批量删除的「回收站二次确认」 | **砍** | 档①已经足够，加一层就是骚扰 |
| 孤儿扫描 | **保留** | 删除的必然伴随物，一个 SQL 搞定 |
| 后台 job + 进度轮询 | **保留** | 导入 5000 张时不做这个会卡死 |
| Pillow | **保留（1 个依赖）** | 导入必须生成缩略图；且只影响导入路径，不影响浏览 |

关于「撤销 = 数据库快照」这一刀，值得展开：v2 到 v3 我一直想给批量操作做撤销，但撤销栈的实现成本（记录每步逆操作、处理冲突、UI）远超收益。而 `gallery.db` 只有几 MB，每次批量操作前 cp 一份，恢复就是 cp 回来。**用文件系统解决应用层问题，是奥卡姆的典型用法。**

## 六、终局思维：三年后这四类操作会长什么样

| 三年后 | 对**现在**的要求 |
| --- | --- |
| 导入变成「多源持续同步」（几个目录 + 几个 API 自动进） | 导入必须幂等、可重跑、有 `source_path` 记录 |
| 最大的修改量来自 **AI 批量打标**，不是手改 | `item_tag.source` 必须区分 `ai`，且能按 source + 批次整体删除 |
| 会想「清理 5000 张垃圾图」 | 批量操作的条件必须来自筛选，不能只支持手选 id |
| 会想「把某个筛选结果导出成训练集」 | 导出范围必须支持筛选，不能只有全库 |
| 会换机器、加外置盘 | `asset.volume` 留字段（v2 已留） |

终局视角最重要的一条：**所有写操作都要能被「批量 + 筛选」触发**。这一条同时满足了「清理垃圾」「AI 打标」「导出数据集」三个三年后的需求，而且不需要现在多写一行代码——只要接口签名设计成 `{filter, action}` 而不是 `{ids, action}`。

## 七、全局思维：四类操作与现有资产的关系

| 关系 | 结论 |
| --- | --- |
| 修改 vs `manifest.json` | manifest 降级为「初始快照，不再更新」。**单向：DB → manifest，绝不反向** |
| 删除 vs `tools/verify.py` / `release.py` | 因为 `sites/` 不物理删，旧链路永远通过。这就是 §3 那条硬约束的第二个收益 |
| 导入 vs 现有 6 站 | 新素材进 `library/`，与采集素材**物理隔离**，永远不会污染旧链路 |
| 导出 vs `release.py` | 发布时用 `export_manifest.py` 从 DB 生成 manifest 喂给旧 `release.py`，旧代码零改动 |
| `tools/` vs `index/` | 明确分工：`tools/` 只服务「发布静态站」，`index/` 服务「日常管理」。**单向桥接，不双写** |

全局思维还有一个反向提醒：**不要为了和 `awesome-ai-video-prompts`、`PromptDirector-Curated` 共享素材语义而提前抽象。** 导出 CSV 就是对外接口，谁要谁来接。

## 八、二八法则：四类操作的顺序，和 v2 不一样

按「不做会不会死」排，而不是按频率：

| 操作 | 频率 | 不做会怎样 | 成本 |
| --- | --- | --- | --- |
| 导出 CSV | 低 | **数据被锁死，你不敢投入打标** | 1 小时 |
| 导入 | 低（但被成本压低） | 库是死的 | 1 天 |
| 修改元数据 | 高 | 库是乱的 | 1 天 |
| 删除 | 极低 | 库会越来越脏，但不致命 | 半天 |

**最有意思的结论：导出应该最先做。**

它不是功能，是**心理前提**。如果我知道「22k 条标注随时能导出成 CSV」，我才敢投入几百小时去标注。反过来，如果数据只能躺在某个 SQLite 里、没有出口，任何理性的用户都不会往里面投入。

而它只要 1 小时——因为「6 份 manifest → 合并成一张统一 CSV」本身就是映射表的验证，是 Step 1 的前置工作。**最便宜的一步，恰好在最前面。**

## 九、修正后的实施顺序

| 步 | 内容 | 投入 | 停下来会得到 |
| --- | --- | --- | --- |
| **S0** | `export.py`：6 份 manifest → 统一 CSV（验证字段映射） | 1 小时 | 一份能进 Excel 的全库清单，映射表已验证 |
| **S1** | `index/`：SQLite + 数据驱动同步 + 8 个只读端点（v2 的 Step 1） | 半天 | 可程序化查询的库，80 MB `gallery.js` 可删 |
| **S2** | 修改：单字段 + 标签 + 按筛选批量 + 批量前快照 | 1 天 | 「管理」这个动词成立 |
| **S3** | 导入：拖拽/扫描 → `library/`，含缩略图与 job 进度 | 1 天 | 库是活的 |
| **S4** | 删除三档 + 孤儿扫描 | 半天 | 库能自我清洁 |
| **S5** | 导出文件到目录（按筛选） | 半天 | 能喂 ComfyUI |
| **S6** | 跨集合 SPA（v2 的 Step 3） | 2 天 | 才叫「素材管理器」 |

核心 S0–S5 约 4 天，**每一步都能停**。S0 一小时就能看到东西，这是刻意的——先给正反馈，再谈架构。

## 十、数据模型增补（v2 的 8 张表 → 9 张）

```sql
-- 新增字段
asset.source_kind   TEXT NOT NULL DEFAULT 'collected'   -- collected | own
asset.status        TEXT NOT NULL DEFAULT 'ok'          -- ok | missing | superseded
asset.volume        TEXT                                -- 预留：外置盘/离线卷
item.meta_json      -- 内含 source_path（导入来源目录）

-- 新增表
job(id, kind, total, done, status, error, started_at, ended_at)
-- kind: import | export | scan；导入/导出/孤儿扫描的进度载体
```

三条与写操作直接相关的约束：

1. `source_kind='collected'` 的 asset **禁止**物理删除（在 `store.py` 里断言，不靠 UI 约束）
2. `status='superseded'` 的 asset 不参与默认查询，但保留在三档图解析里（回滚用）
3. `job` 表的记录超过 7 天自动清理（它只是进度载体，不是日志）

## 十一、风险

| 风险 | 缓解 |
| --- | --- |
| 批量操作写错条件，全库被改 | 执行前返回影响行数 → 用户确认 → 自动快照 |
| 误删物理文件 | 结构上只允许删 `library/`；档③ 二次确认 + 显示释放体积 |
| 导入 5000 张时 UI 卡死 | 后台 job + 轮询；每张独立事务，可中断 |
| SQLite 在 `ThreadingHTTPServer` 下的写锁冲突 | `PRAGMA journal_mode=WAL` + 单写线程（写操作串行化） |
| `library/` 里的文件被外部手动移动 | 孤儿扫描兜底，标 `missing` 而非报错 |
| 缩略图生成失败（损坏文件） | 单张失败不中断整批，记入 job 的 error 列表 |

## 十二、需要你确认的两件事

1. **重心仍是 (a) 浏览 + (b) 打标吗？** 如果是 (c) 创作取素材，S5（导出到目录）要提到 S3 之前；如果是 (d) 沉淀自己的图，S3（导入）要提到 S2 之前。
2. **是否接受 1 个第三方依赖（Pillow）？** 不接受的话可以退化成「导入不生成缩略图，网格直接用原图」——但 2 MB 的 PNG 铺满网格会卡，实际不可用。也可以手写 PNG/JPEG/WebP 头解析 + 只在需要时懒生成，但那就从 1 个依赖变成 300 行自维护代码。**建议接受。**

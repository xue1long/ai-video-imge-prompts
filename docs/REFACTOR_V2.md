# 重构方案 v2：用六个思维模型重推一遍

> 本文取代 [`REFACTOR_TO_WEBUI.md`](REFACTOR_TO_WEBUI.md)。v1 的结论（FastAPI + 6 天五阶段）已被本文第七节的自我批判推翻。
> **续篇：[`REFACTOR_V3_WRITE_OPS.md`](REFACTOR_V3_WRITE_OPS.md)** —— 修改 / 导入 / 删除 / 导出四类写操作。v2 假设世界是只读的，v3 修正了这个前提并重划库的边界。
> 状态：**待确认**，未改动任何代码。日期：2026-10-31

## 一、第一性原理：把问题拆到不能再拆

剥掉「WebUI」「素材管理器」「后端」这些词，剩下的事实只有四条：

1. **图已经在正确的位置上。** 29,185 张图 + 三档尺寸（thumb/mid/full）躺在 `sites/*/{thumbs,mid,img,png}`，共 11.63 GB。不需要「导入」，不需要「搬迁」——只需要**索引**。
2. **元数据已经是结构化的。** 6 份 `manifest.json` 是合法 JSON，字段齐全，只是彼此不自洽。不需要「提取」，只需要**对齐**。
3. **瓶颈不是存储、不是并发、不是性能。** 581 张/秒的本地磁盘读取、22k 条记录的 SQLite 查询都是毫秒级。真正的瓶颈是**你和这些图之间的交互带宽**——想找一张「侧面视角、坐姿、线稿」的图时，你能不能在三秒内看到它。
4. **单用户 + 本地 + 无部署。** 没有多租户、没有权限、没有缓存一致性、没有横向扩展。

**推论（反直觉）**：单用户本地应用里，「后端」这个概念是虚构的。所谓 API，只是「读文件和读 SQLite」的一层包装。所谓 HTTP，只是让浏览器能访问文件系统的协议适配器。

所以真正缺的只有三样东西：

| 缺什么 | 现状 | 最小补法 |
| --- | --- | --- |
| 一个可查询的索引 | 6 份 JSON，每次筛选全量扫 | SQLite（Python 自带 `sqlite3`） |
| 一个能改索引的界面 | 写操作只能进浏览器本地存储 | 10 个 HTTP 端点 |
| 一套跨集合的筛选语义 | 6 套互不相通的筛选项 | tag 带 namespace |

**第一性原理砍掉的**：`server/` 目录树、Pydantic 模型层、adapter 类继承、迁移框架、导入流水线。这些都是「应用该有的样子」的想象，不是问题本身。

## 二、批判性思维：先审我自己的 v1 方案

v1 有七个问题，按严重程度排：

| # | v1 的做法 | 问题 | 性质 |
| --- | --- | --- | --- |
| 1 | 没确认「管理」的动词，就把浏览/打标/导入/衍生四种诉求全包进来 | 需求膨胀。四种诉求对应四种架构，全都要 = 都要得不好 | **最严重** |
| 2 | 把 `sha256` 去重 11.63 GB 放进 P1 关键路径 | 自造需求。你没说过要查重，我因为「素材管理器都该去重」加了它 | 伪需求 |
| 3 | 推荐 FastAPI + uvicorn | 因为「我熟悉、这是标准做法」，不是因为必要。而本仓库 8 个 `tools/` 全是标准库 | 论证不成立 |
| 4 | 说「渐进式重构，不推倒重写」，实际动作是弃用 6 套 UI + 新建 `server/` | 自我矛盾。诚实说法是「保留资产，重写应用」 | 表述失真 |
| 5 | 把「photoai.life 还发不发」列为架构拍板项 | 它是独立小事，不该占主线位置，更不该影响架构 | 权重错配 |
| 6 | `asset` 设计成 `item` 的从属（`asset.item_id`） | 表达不了 `pose` 与 `pose-depth` 同源（同一姿势的原图与深度图分属两个集合） | **设计缺陷** |
| 7 | 三档图写死成 `thumb_path / mid_path / full_path` 三列 | 6 个站的 tiers 本来就不一致（`thumb,full` / `thumb,img,png` / `thumb,mid,full`），照抄进 schema 就是给自己挖坑 | **设计缺陷** |

第 6、7 条是 v1 真正的技术错误，本文第五节修正。

第 1 条是最该被批判的。**「素材管理器」在你的语境里有四种可能，架构完全不同：**

| 诉求 | 你要做的事 | 需要的架构 |
| --- | --- | --- |
| (a) 浏览/找图 | 打开就看，按视角/系列筛 | **现有页面已经能做 80%** |
| (b) 打标/整理 | 给图打标签、收藏、分组 | 需要写接口，但不需要新 UI |
| (c) 创作时取素材 | 复制 prompt、拖进 ComfyUI | 需要快，不需要全 |
| (d) 持续沉淀 | 自己生的图不断进来 | 需要同步器，不是迁移脚本 |

v1 默认你四种全要，于是设计了一个能覆盖四种的系统。**但覆盖四种的系统，每一种都做得不如专做一种。**

## 三、奥卡姆剃刀：逐个问「没有它行不行」

| 实体 | 没有它会怎样 | 裁决 |
| --- | --- | --- |
| FastAPI | 手写路由，20 个端点以内不痛 | **剃掉**，用 `http.server` |
| uvicorn | 同上 | **剃掉** |
| Pydantic 模型层 | `dict` + 手写校验，22k 条规模无压力 | **剃掉** |
| 6 个 adapter 类 | 6 份一次性代码，跑完即废 | **剃掉**，换成一张映射表 |
| `sha256` 去重 | 没有它，图库照常用 | **剃掉**（除非你要） |
| 操作日志 / 撤销 | 误删有几秒可反悔 | **剃掉**，删除改软删即可 |
| `saved_search` 表 | 少一个「保存当前筛选」按钮 | **剃掉** |
| 静态站导出器 | `photoai.life` 不更新 | **剃掉**，真要发再说 |
| 图片搬迁到 `library/` | 路径不统一，但能用 | **剃掉**，原位索引 |
| SQLite | 只能回到 6 份 JSON 全量扫 | **保留**（唯一必须新增的实体，且是标准库） |
| Pillow | 不能生成新缩略图 | **剃掉**，三档图已在盘上 |
| Node / npm | 前端没有构建步骤 | **剃掉** |

剃完剩下：`sqlite3` + `http.server` + `json` + 现有前端。**零新增依赖。**

关于 FastAPI 要诚实：它的价值是真的（自动校验、自动文档、依赖注入）。但它服务于「多端点 + 多开发者 + 长期演进」。单人本地 10 个端点用不上。**给一个明确的切换触发条件**（见第八节），而不是「永远不用」。

## 四、终局思维：三年后这个库长什么样

| 三年后的现实 | 对**现在**的架构要求 |
| --- | --- |
| 素材从 29k 涨到 60k+（自己生的图、新采集的源） | 导入必须是**持续能力**，不是一次性迁移脚本 |
| 会出现派生图（同一张图的深度图、边缘图、重绘版） | 派生关系要能表达，不能写死三档 |
| 会想要「用起来」而不只是「看着」：复制 prompt、导出到 ComfyUI | prompt 必须是一等字段，且原文与译文分离 |
| 会换机器、加外置盘 | 路径要能表达「所在卷」，要能整库搬迁 |
| 元数据来源会混杂（内置/手动/AI/上游） | 每条标注要能追溯来源 |

v1 的方案在这五条上踩了两条（第 2、5 条）。修正见第五节。

终局思维还有一个结论：**不追求一次到位。** 三年后长什么样，不影响今晚做什么。真正要做的只是「别把路堵死」——加字段比改架构便宜一百倍。

## 五、全局思维：它在你的工作流里的位置

你的真实链路是：

```
生图（MJ / imge-2 / nanobanana / ComfyUI）
   ↓
筛选（这个库在做的事）
   ↓
复用 prompt / 参考图 → 产出
```

这个库是链路的**中间层**，不是终点。同族还有 `awesome-ai-video-prompts`（作品索引）、`PromptDirector-Curated`（prompt 目录），它们和本库共享「素材 + prompt + 标签」的语义。

但全局思维的另一半是：**现在不要为了生态提前抽象。** 先让本库跑通，用 CSV/JSON 导出作为对外接口，谁需要谁来接。提前统一的代价是三倍，收益是负数。

全局思维还要求算「不重构的成本」：

| 不重构 | 代价 |
| --- | --- |
| 加素材 | 每次重跑 build，`prompts` 站要重新下发 80 MB |
| 打标 | 只能进浏览器本地存储，换浏览器即丢 |
| 跨站找图 | 6 个页面分别开，搜 6 次 |
| 长期 | 标注资产永远是零 |

**判断**：如果你只用来看图，不重构是对的。如果你想用它做创作工作流，重构是值得的——但只需要做 20%。

## 六、二八法则：砍到只剩 80% 价值的那 20%

按真实使用频率排序：

| 功能 | 频率 | 现状 |
| --- | --- | --- |
| 浏览 + 分面筛选 | 每次打开 | ✅ 已能 |
| 关键词搜索 | 高频 | ✅ 已能 |
| 看大图 | 高频 | ✅ 已能 |
| 复制 prompt | 高频（创作时） | ✅ 已能（仅 prompts 站） |
| 收藏 | 中频 | ❌ 只在浏览器本地存储 |
| 打标 | 低频，但价值高 | ❌ 同上 |
| 跨集合搜索 | 中频 | ❌ 完全没有 |
| 上传/导入 | 低频 | ❌ 只能重跑构建 |
| 删除 | 极低频 | ❌ |
| 相似图 / 去重 / AI 打标 | 极低频 | ❌ |

**20% 的功能 = 前六行。其中四行现在就能用，一行（收藏）只需换存储，一行（跨集合搜索）需要索引。**

于是结论变得很小：**80% 的价值 = 一个索引 + 两个写接口。不需要「重构成 WebUI 素材管理器」这个宏大命题。**

v1 花了 6 天做五阶段，其中真正命中这 20% 的只有 P1 和 P3 的一小半。

## 七、六个视角的冲突与裁决

| 冲突 | 甲方 | 乙方 | 裁决 |
| --- | --- | --- | --- |
| 要不要「持续同步」 | 第一性原理：现在不需要 | 终局思维：三年后必须要 | 现在不写代码，**schema 留字段**（`asset.volume`、`item.ext_id`、`tag.source`） |
| 要不要「元数据可追溯」 | 奥卡姆：剃掉 | 终局：必须留 | 砍功能、**留字段**（`item_tag.source` 一列，成本为零） |
| 到底做什么 | 批判性：先确认动词 | 二八：80% 是浏览 | **先做浏览那 80%**，即「索引 + 收藏入库」，打标等跑顺了再定 |
| 前端要不要重写 | 奥卡姆：复用现有 | 全局：跨集合需要统一视图 | **Step 1/2 不动前端**；Step 3 才做统一视图，且从现有最好的一套改 |
| 要不要框架 | 奥卡姆：不要 | 批判性：原生 JS 写批量会痛 | **先不要**，等 Step 3 遇到具体痛点再引入（届时只换前端，API 不变） |

## 八、收敛后的方案：三步，每步都能停

### Step 1 · 索引层（半天～1 天）

新增三个文件，不动任何现有代码：

```
index/
├── store.py    # SQLite schema + 查询函数（无 ORM）
├── sync.py     # 6 站 manifest → DB，数据驱动映射
└── serve.py    # http.server + 8 个端点 + 静态文件
```

`sync.py` 的核心不是 6 个 adapter，而是**一张映射表**：

```python
SOURCES = {
  "portrait": {"manifest": "sites/portrait/manifest.json",
               "title": "风格", "facets": {"分区": "分区", "发型": "发型", "风格": "风格"},
               "files": {"thumb": "thumb_path", "full": "full_path"}},
  "pose":     {"title": "姿势名_zh",
               "facets": {"系列": "系列", "分類": "分類", "视角": "视角"},
               "files": {"thumb": "thumb_path", "full": "full_path"}},
  ...
}
```

**验收**：`curl "http://127.0.0.1:8765/api/items?q=坐姿&facets=视角:正面&limit=20"` 返回正确结果；`prompts` 站的 80 MB `gallery.js` 可以删除。

**收益**：之后加素材只需跑一次 `sync.py`（秒级），不再重跑构建、不再重新下发 80 MB。

**这一步就能停。** 如果停在这里，你得到的是「可以程序化查询的素材库」，现有页面照旧能用。

### Step 2 · 标注入库（1 天）

- 收藏 / 手动标签 / 软删除 → 写进 `gallery.db`
- 前端改 3 个函数（读初值、写入、删除），UI 完全不动
- 新增 `GET /api/export.csv` —— 全部标注导出，可备份、可迁移、可进 Excel

**验收**：换浏览器标注仍在；导出的 CSV 能完整还原；数据库文件可单独备份。

**这一步就能停。** 如果停在这里，你得到的是「标注终于不会丢的图库」——这已经解决了现状最痛的两个点。

> 注：`mj-gallery` 的旧标注存在浏览器里，页面目录已空，理论可从同源 devtools 读回，实操价值低。按从零开始设计。

### Step 3 · 统一视图（2 天，按需）

- 一套跨集合 SPA：左侧集合树 + 顶部搜索 + 分面 chips + 网格 + 详情抽屉
- 从 `shared/pose_gallery.py` 生成的产物里抽 CSS/JS（那套已经打磨过虚拟滚动、灯箱、双主题），不重画
- 批量操作（框选 / Shift 连选 → 批量打标、收藏、移动集合）
- 上传 / 扫描目录入库（按路径去重，不算 sha256）

**验收**：22k 条下滚动无掉帧；筛选 <200ms；首屏可交互 <1s（对比现在解析 80 MB JSON 要 3s）。

**这一步之后才叫「素材管理器」。** 但只有前两步跑顺了，这一步才值得做——因为它解决的问题（跨集合浏览）在现状里只能排第三。

## 九、修正后的数据模型（8 张表，v1 是 9 张 + 3 个错误）

```sql
collection(slug, name, sort)                     -- 6 个原有 + 自建

asset(id, path, volume, bytes, width, height, mime)
-- 物理文件，独立存在，不隶属于 item

derivative(asset_id, kind, path, width, height)
-- 同一视觉内容的不同尺寸：thumb / mid / full / png
-- 替代 v1 的三列写死（6 站 tiers 本来就不一致）

item(id, collection, ext_id, title, prompt, prompt_raw,
     author, source_url, published_at, model, meta, deleted_at)
-- 一条素材记录；ext_id 存原 manifest id

item_asset(item_id, asset_id, role, ordinal)     -- 多对多
-- 一张图可属多个作品；一个作品可含多图

tag(id, ns, name)                                -- ns: 系列/视角/发型/分区/分类…
item_tag(item_id, tag_id, source)                -- source: builtin / manual / ai
fav(item_id, at)
```

三处修正，都来自前六个视角暴露的问题：

| 修正 | 起因 | 解决什么 |
| --- | --- | --- |
| `asset` 独立 + `item_asset` 多对多 | 终局思维 | `pose` 与 `pose-depth` 是同一姿势的原图与深度图，分属两集合却同源；从属关系表达不了 |
| `derivative` 表替代三列 | 实证（6 站 tiers 不一致） | 未来加派生图（边缘图/重绘版）不用改 schema |
| `item.ext_id` + `asset.volume` | 终局（换机器/加盘） | 跨站同源关联、整库搬迁、离线卷标记 |

## 十一、不做什么（明确写下来）

- 不算 sha256、不做去重报告（除非你明确要）
- 不做操作日志、撤销、`saved_search`
- 不做静态站导出器（`photoai.life` 发不发是独立小事）
- 不搬图片、不改 `sites/` 下任何现有文件
- 不引入 Node、不引入 pip 依赖
- 不做相似图、AI 打标、以图搜图（这些是 20% 价值里的尾巴）

## 十二、技术选型的切换阈值

标准库方案不是信仰，是当下的最优。出现下面任一情况就换 FastAPI：

- 端点数超过 20 个
- 需要给别的机器/别人访问（要鉴权、要 OpenAPI 文档）
- 需要写操作并发（多端同时改）
- 需要流式响应（大文件分片、视频）

换的时候只替换 `serve.py`，`store.py` 与数据库不动 —— 这是分层带来的保险。

## 十三、实现细节里的坑（提前记下）

1. **`http.server` 的**：必须用 `ThreadingHTTPServer`（否则一个慢请求阻塞全部）；`SimpleHTTPRequestHandler` 默认不支持 Range 请求（图片无影响，视频会有）；Windows 上 `mimetypes` 可能不认 `.webp`，需手动注册。
2. **中文路径**：`costume/thumbs/春/SPR-0001.webp`、`pose/thumbs/全身1人・セクシー系/立ち/P001/正面.jpg`。URL 必须 `quote` 编码，DB 存原样；Windows 长路径注意 `\\?\` 前缀。
3. **`prompts` 站的多图**：`manifest` 里同一 `id` 出现多次（`i13983_1` / `i13983_2`），同步时必须按 `id` 聚合成一个 item + 多个 asset，否则 item 数会虚高到 22,268 而非 15,118。
4. **SQLite 并发**：`http.server` 多线程 + SQLite 默认 `check_same_thread` 会报错，用「每线程一个连接」或单写锁。
5. **软删除**：`deleted_at` 非空即回收站；彻底删除才动磁盘，且二次确认。

## 十四、需要你确认的一件事

本文按 **(a) 浏览 + (b) 打标** 这两个诉求推进（Step 1 → Step 2）。如果你的真实重心是 **(c) 创作时取素材** 或 **(d) 持续沉淀自己生成的图**，Step 的优先级要重排：

- 重心 (c) → 优先做「prompt 快速复制 + 一键发送到剪贴板/ComfyUI」，`prompts` 站先行
- 重心 (d) → 优先做「扫描目录 + 增量同步 + 重复提示」，而不是打标

# SPEC · 本地素材管理器（ai-image-gallery → WebUI）

> 来源：[`REFACTOR_V6_LOCKED.md`](REFACTOR_V6_LOCKED.md)（22 条决策经三轮质询锁定）。

> 日期：2026-10-31

## Problem Statement

我维护着 5 个 AI 绘画参考图库，共 22,020 条素材、29,185 个文件、11.63 GB，全部由一套 Python 脚本在构建期编译成 6 个独立的静态页面。这套做法在我只是「发布」的时候够用，但我真实要做的事情是**创作时取素材**，于是处处卡住：

- **找一个素材要翻 6 个站**。每个集合有自己的搜索框，同一批 288 个姿势的原图与深度图分散在两站，跨集合找「正面视角的坐姿」做不到。
- **加一张自己生成的图要重跑整个构建**。10 分钟的构建只为加一个文件，于是我干脆不加——库不再生长。
- **标注存在浏览器里**。收藏和手动标签躺在 `localStorage`，换个浏览器全丢，既不能查也不能导出。我不敢往里投入时间。
- **提示词数据是 79 MB 的一个 JS 文件**。为了改一个标签要重新下发 79 MB，首屏要等 3 秒。
- **数据模型按「一文件一记录」组织**。一条提示词带两张图就变成两条互不相干的记录，收藏了其中一条，另一条不知道。
- **取出去的路径是死的**。看到想要的图，只能右键另存，再手动挪进 ComfyUI 的 input 目录。

## Solution

把「构建期编译」换成「运行期服务」：

- **一个 SQLite 数据库成为唯一真相源**，素材文件原位索引、不搬家。6 份互不相同的 manifest 同步进统一模型，标注、收藏、导入记录都写进同一个库。
- **11 个 HTTP 端点**提供全部能力，接口定死之后只增不改。
- **一个单页界面**统管全部集合：顶部一排集合胶囊 tab、左栏分面与添加素材、中间网格、右栏详情与操作。四段（沉淀／浏览／打标／取素材）全部落在一页，不切路由。视觉与六个静态站同源（同一套颜色变量、胶囊控件、2:3 不裁切卡片、浅／深双主题）。
- **库的边界写进结构**：采集素材所在的目录只读、永不物理删除；新增的素材目录可写、允许删除。误删那批要重下几小时的素材在结构上不可能发生。
- **取素材有两个出口**：复制 prompt 原文（逐字符一致）、把原图硬链接到配置好的目标目录（同盘零拷贝）。

## Implementation Decisions

### 单一测试接缝：HTTP JSON API

全部新行为都通过「起服务 → 发真实 HTTP 请求 → 断言 JSON」验证，不 mock 内部函数、不断言内部数据结构。测试用的数据根是一个临时目录，里面放**极小**的假 manifest（每集合 2–3 行）与 1×1 像素的占位图，因此测试不需要 11 GB 真实素材。同步器、数据库、前端都通过这一个接缝被间接覆盖。

### 数据模型（9 张表）

```sql
collection(slug PK, name, sort)                    -- 6 站 + own（导入素材），共 7 行
asset(id PK, path UNIQUE, volume, bytes, width, height, mime, status)
derivative(asset_id, kind, path, bytes, width, height, PK(asset_id, kind))
item(id PK, collection, ext_id, title, title_alt,
     prompt, prompt_raw, author, source_url, published_at, model,
     generator_meta, search_blob, last_used_at, use_count, meta, deleted_at)
item_asset(item_id, asset_id, role, ordinal, PK(item_id, asset_id))
tag(id PK, ns, name, name_zh, UNIQUE(ns, name))
item_tag(item_id, tag_id, source, PK(item_id, tag_id))
fav(item_id PK, at)
kv(key PK, value)
```

约束与语义（每条都是一条决策，不是随意选择）：

- `asset.volume ∈ {sites, library}` 决定能否物理删除；`sites` 永不物理删除。
- `asset.status ∈ {ok, missing}` **只由维护命令改写**，写入路径永不碰它。
- `item.deleted_at` **只表示视图隐藏**，与 `asset.status` 互不改写。
- `item.id` 形如 `集合:外部ID`（`pose:P018`、`own:2026/10/文件名`）。
- `source_kind` 语义由 `volume` 承担，不额外建 `source` 表。
- `derivative.kind ∈ {thumb, mid, full, img, png}`——六个集合的档位本来就不一致，不能写死三列。

### 端点契约（11 个，定死只增不改）

| # | 端点 | 语义 |
| --- | --- | --- |
| 1 | `GET /api/collections` | 集合清单与计数 |
| 2 | `GET /api/items?collection&q&facet&page&size&sort` | 分页列表；`size` 默认 120、上限 200 |
| 3 | `GET /api/items/{id}` | 详情：全字段 + 各档资产 + 标签 |
| 4 | `GET /api/facets?collection` | 分面与计数，带中文名 |
| 5 | `POST /api/items/{id}/tags` `{op,ns,name}` | 加/删标签，同步重算检索列 |
| 6 | `POST /api/items/{id}/fav` `{on}` | 收藏开关 |
| 7 | `POST /api/import` | multipart 文件、`{url}` 链接或 `{path}` 本机路径；落库 + 缩略图 + 读文本块 |
| 8 | `POST /api/send` `{item_id,target}` | 硬链接／复制到配置目录 |
| 9 | `GET /media/{relpath}` | 图片（带 Last-Modified／ETag），拒绝越界路径 |
| 10 | `POST /api/items/{id}/replace` | 同上三种来源；新图进 `library/` 排到主图位（`ordinal=-1`、`role=replaced`），原图不删 |
| 11 | `POST /api/items/{id}/attach` | 同上三种来源，**multipart 可一次带多张同名 `file` 字段**；新图进 `library/` 排在图条末尾（`role=user`、`ordinal` 从 10000 起），主图与采集原图都不动 |

补充两条被实现逼出来的约束（都是实测撞到的，不是设计推演）：

- **图片路径必须以 `sites/<集合>/` 为前缀**：manifest 里的 `thumb_path` / `full_path` 是**站点相对**路径。`pose` 与 `pose-depth` 的字段一字不差，不前缀会被当成同一批文件去重掉（实测资产数从 29,185 掉到 27,746）。
- **作品 id 必须 URL 安全**：导入素材的 id 用 `own:202610-文件名`（年月连写），不能带 `/`，否则 `/api/items/{id}` 的路由在第一个斜杠处就断开了。

统一错误体 `{"error": code, "detail": str}`。HTTP 400／404／409／415／500。已定错误码：`bad_facet`、`bad_tag`、`bad_request`（含链接非法／下载失败）、`unknown_target`、`source_missing`、`unsupported_ext`（扩展名不支持，或链接指向的不是图片）、`duplicate`（带 `existing_id`）、`builtin_tag`（试图删除上游分面）、`not_found`、`internal`。

**端点 7、10、11 的取图来源完全一致**，实现里共用同一个函数（`incoming_source` / `incoming_sources`）：multipart 上传（浏览器选文件／剪贴板贴图）、`{url}` 链接、`{path}` 本机路径。链接只认 `http`／`https`——`file://` 等于「读本机任意文件」，不做；下载上限 40 MB、超时 20 s，落盘前先用 Pillow 开一次，坏图不进库。

**「替换」不删原图**：新文件进 `library/YYYY/MM/` 并排到主图位（`item_asset.ordinal=-1`、`role=replaced`），采集来的原图一个字节都不动。因此这条端点对 `sites/` 只读区仍然合法，也可以随时反悔——把新记录删掉就退回原图。

**「追加」与「替换」是两件事**（端点 11 vs 端点 10）：一条提示词的成图是上游给的，用户自己用别的模型跑出来的图属于「再加一张」，不该顶掉第一张。所以 `attach` 用的是正序大基数——采集图的 `ordinal` 从 0 起，用户图从 `USER_ORDINAL_BASE = 10000` 起递增，两批序号永远不撞，图条天然是「上游原图在前、自己加的在后」。`primary_asset_path` 取 `ordinal` 最小的一条，因此 `attach` 不会改变主图，送素材、复制 prompt 的行为一个字都不变。

**用户图要跨同步活下来**：`prompts:` 这类采集集合每次 `sync` 都会 `DELETE FROM item` 再重建，`item_asset` 跟着级联消失；但图片文件在 `library/`（`volume=library`）不会被删。所以 `PRESERVE_SQL` 额外把 `role=user` 的链接按 **路径** 存进临时表 `_keep_link`，`restore_user_data` 在采集重建完之后按 path 找回 asset id 重新挂上。**判重按文件内容 SHA-1**，不看字节数与宽高——两张同尺寸图片很容易长度完全相同（实测两张 4×4 PNG 都是 100 字节），按元数据判会把第二张当重复吞掉。判重范围只限同一条素材：不同提示词配同一张图是正常用法。

标签形状是 `[命名空间, 原名, 中文名, 来源]`，来源取 `builtin`（上游分面）/`manual`（手打）/`auto`（导入时自动打的「未审」）。上游分面不允许手工删除（`del` 会得到 `409 builtin_tag`），因为它同步一次就会回来。

**视图隐藏复用端点 5**，不新增端点：加 `状态:隐藏` 标签即隐藏，删即恢复。`item.deleted_at` 只在这一条路径上写，列表与分面默认过滤它，`include_hidden=1` 可查回。整个过程不碰任何文件。

### 检索

`item.search_blob` 是冗余列 = `title + title_alt + prompt_raw + 全部分面名（原语言与中文）`，写入时规范化（换行→空格、合并空白）。搜索只 `LIKE` 这一列，不 join `item_tag`。打标后同一条 SQL 内重算。

### 中文化

姿势系的 288 个中文姿势名进 `item.title_alt`；26 个分类、4 个系列、视角文案进 `tag.name_zh`。三个来源都是仓库里已有的翻译表，不新增人工翻译。

**标题口径统一为**：`title` 是展示名（中文优先），`title_alt` 是原文。`shisei` 的 manifest 本来就是这么排的；姿势两站由翻译表把 `姿势名` 换成中文进 `title`，日文原文进 `title_alt`。检索列两者都收，所以中日两种写法都能搜到。

### 边界与落盘

- 采集素材目录只读；`library/年/月/原文件名` 可写，重名追加 `-2`，不改名成哈希。
- 送素材优先硬链接，跨盘失败退回复制；重名追加 `-2`；**绝不清空目标目录**。
- 数据库、导入素材、快照、配置都不进版本库。

### 同步策略

启动时比对 6 个 manifest 的 `mtime+size` 签名（存在 `kv`），变化才全量重建；22k 行约 14 秒。不做增量 diff——同步不是瓶颈，增量是 bug 来源。

**重建必须保住用户标注**：采集素材的 `item`/`asset` 行会被删掉重建，所以重建前把 `manual`/`auto` 标签、收藏、`deleted_at`、以及 `own` 集合（导入素材）存进临时表，重建后放回。这是「标注不再丢」这条承诺的唯一实现点。

### 界面

单文件单页、原生 JS、零构建。默认「全部」混排，每页 120 条 + 底部「加载更多」按钮（不用自动滚动）。集合切换与搜索变化重置到第一页并滚回顶部。打标即写即报。

视觉沿用 `sites/costume`／`sites/pose`／`sites/shisei` 那一套：`html[data-theme]` 双主题（浅 `#2563eb`／深 `#8fb4ff`，选完记进 `localStorage`，首帧前由内联脚本定下来避免闪白）、radial-gradient 光晕背景、毛玻璃工具条、胶囊 tab 与 chip、`--r:14px` 卡片、`object-fit:contain` 的 2:3 图位。

分面按集合隔离，值超过 48 项的命名空间（如姿势集的「编号」80 项）默认折叠 —— 它更像标识而不是分类，展开会把左栏整个撑满。卡片只显示标题：长 id 会挤掉中文姿势名，编号留给详情。

### 集合顺序与命名

集合顺序沿用现有站点清单的顺序，导入素材作为独立集合 `own`。展示名用中文。

## Testing Decisions

**好测试的标准**：只断言外部可观察行为（HTTP 状态码、JSON 字段、磁盘上文件是否存在与内容），不断言内部函数调用、不断言 SQL 形状、不断言前端 DOM。一个测试如果在重构实现但不改行为时失败，就是坏测试。

**被测试的模块**：全部 11 个端点的正常路径 + 已定错误码路径；同步器通过「建库后端点返回的计数是否正确」间接验证；前端不做 DOM 断言，只通过接口覆盖其依赖。

**测试数据**：临时目录内的迷你数据根（假 manifest + 占位图）。真实 22k 数据的体检**不作为自动化测试**，因为 CI 拿不到图片；真数据核对用维护命令输出，写进 v6 验收表。

**先例**：`tests/run.py` 是标准库 `unittest`、class 按关注点分组、`-k` 过滤、零第三方依赖。新测试沿用同一风格放在独立文件里，可单独运行，不拖慢现有 405 行检查。

**接缝的两处例外**（评审时明确下来的，不是松动）：

1. `sync` / `verify` / `snapshot` 是**命令行工具**，它们的外部行为就是「跑完之后磁盘与数据库变成什么样」，因此允许直接调用其模块函数并断言返回值与后续 HTTP 响应；但凡是服务端能力，一律走 HTTP。
2. 仓库级约定（启动器存在、README 有三条命令、`.gitignore` 覆盖本地数据）只能从文件系统断言。

`test_manager.py` 需要 Pillow（生成缩略图），CI 里先 `pip install pillow` 再跑；`tests/run.py` 保持零依赖。

**不引入 pytest**：现有 CI 只装了 Python，加依赖会让 `tests/run.py` 的「零依赖即可跑」这条性质失效。

## Out of Scope

- 内置图像编辑器（外面有 PS 与生成工具）。
- 版本链 UI、撤销栈、操作日志（留字段 + 数据库快照）。
- sha256 内容去重（「文件名+字节+尺寸」足够）。
- 跨设备同步、多用户、鉴权（单机自用）。
- 与同族项目统一素材语义（CSV 就是对外接口）。
- 静态站点的重写或删除（冻结，代码与产物都留着）。
- 瀑布流布局（等高网格，省掉 22k 文件宽高扫描）。
- Node／前端框架／打包工具。
- 目录监视与自动扫描导入（没有稳定观察目录）。
- FTS5 全文索引（`LIKE` 在这规模下足够，慢了再上）。
- ComfyUI 字段级参数解析（本机不存在该工具，只做通用文本块读取）。

## Further Notes

- **唯一仍开放的信息**：生图工具与图片落盘目录。拿到后「沉淀」段可从「存下来」升级为「连参数一起存」，这属于后续加深，不阻塞本规格。
- **风险**：真实 manifest 里 50 条标题含换行符，规范化只在写入路径做，不改上游数据。
- **实测校准（2026-10-31，真实 22k 数据，以此为准）**：

| 指标 | 规格原写 | 实测 | 说明 |
| --- | --- | --- | --- |
| item / asset / derivative | 22,020 / 29,185 / 60,910 | **22,020 / 29,185 / 60,910** | 三项全中 |
| 首次全量同步 | 2–3 s | **14.2 s** | 原估计过低；签名未变时跳过，日常启动不受影响 |
| `q=座り&facet=视角:正面` | 116 | **116** | 一致 |
| `facet=视角:正面` | 809 | **809** | 一致 |
| `q=cyberpunk` | 160 | **368** | 原测算基于截断到 200 字符的 CSV，真实库不截断，命中更多 |
| `q=座り` | 592 | **606** | 同上 |
| `q=坐姿` | 148（接中文化前） | **778** | 中文别名接入后大幅提升，符合预期 |
| 列表首屏（120 条） | 未定 | **139 ms** | 每条要查缩略图/收藏/标签 |
| 分面计数 | 未定 | **32 ms** | |
| 带关键词的检索 | <50 ms | **360–700 ms** | `LIKE` 扫 33 MB 检索列，见下 |
| 数据库体积 | 未定 | **141 MB** | 其中 `search_blob` 占 33 MB |

- **关于检索延迟**：`<50 ms` 是规格写得太乐观。FTS5 的 trigram 分词**救不了这里**——中文两字词（「坐姿」）不足 3 个字符，`MATCH` 直接查不到，而这恰是最常用的查询形态。所以 M2 保留 `LIKE`，把「嫌慢再优化」列为 M3 选项：可选手段是把 `search_blob` 里的 prompt 截到 200 字符（体积降到约 8 MB，代价是长 prompt 尾部不可搜），而不是上全文索引。

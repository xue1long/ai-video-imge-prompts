# 落地页清理只删孤儿文件，不做整目录重建

`shared/landing.py` 原本用 `shutil.rmtree` 把每个分面目录整个清掉再重建。2026-11-04 改为：读上次构建记录的 `data/landing.json` 里的页面清单，算出「上次有、这次没有」的差集，只删这几个孤儿文件（外加清空壳目录）。页面集合不变时，一次构建**一个文件都不删**。

## 为什么改

WorkBuddy 运行时给删除 API 加了批量闸门：一次调用删够 50 个文件就 `SystemExit(1)`，把构建打断在中间，留下一片半删状态。整目录 `rmtree` 一个分面目录就是几十个文件，必然触发。

关键在于闸门的计数方式 —— 它**按 tool call 累计文件数**（`safe-delete-bulk-guard.cjs:344` 的 `totalCount = request.count + deleteCount`），不是按单次调用的文件数。所以「改成逐文件删」并不能规避：50 次单文件删照样累计到 50。

真正能让闸门不触发的，是**正常构建删 0 个文件**。

## 考虑过的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 逐文件删孤儿 | 看起来绕开了闸门，但闸门累计计数，50 次单文件删照样触发 |
| 让构建时关掉闸门 | 构建脚本不能依赖运行时的环境变量；CI 上没有这个变量，行为会不一致 |
| 保留整目录 rmtree，接受触发 | 每天的构建随机失败，且失败点是「删到一半」，破坏性大 |
| 把清理挪到构建之后单独跑 | 清理与生成分离后，「构建产物与仓库一致」这条 CI 闸门就没法在一次构建里验证 |

## 后果

- 落地页的分面目录里若混进了非 `index.html` 的文件，**不会被清掉** —— 空目录清理用 `os.rmdir`，只收空壳。这是刻意的：别人的东西不该被顺带删。
- 分面改名或删除时，只删真正的孤儿那一个文件，不会牵连同目录下其它分面。
- `data/landing.json` 从「记录有哪些目录」升级为「记录上次生成了哪些页面」，成为清理的差集基准。它是入库文件，行尾必须固定（`newline="\n"`），否则 Windows 与 Linux 的产物不一致，CI 的产物比对会红。
